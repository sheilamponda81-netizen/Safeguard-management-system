### @typescript-eslint/no-explicit-any — 174 of 361 fixed across two passes, 187 classified below

Per the explicit priority order given for this task (payroll processing → payslips → payments → terminal dues → attendance → auth/session → authorization → Supabase RPC responses → Supabase query results → employee/security-personnel writes → audit logging → payroll-affecting settings), `any` remediation worked through that list file by file rather than mechanically replacing every occurrence. **One safe error-normalization helper, `getErrorMessage(error: unknown): string` in `utils/errorHandler.ts`, now backs every fix below that touched a `catch` block** — it distinguishes an `AppError` (returns its authored `userMessage`), a Postgrest/Postgres error (detected via its `code` field, mapped through a fixed safe-message table — raw `.message`/`.details`/`.hint` are never echoed, since those can contain table/constraint names), and a plain `Error`/string (application-authored, since Postgrest errors always carry `code`, so anything without one was thrown by this app's own code and is safe to show verbatim). The old, separate `handleError`/`withErrorHandling` (confirmed dead code, duplicating the same concern) were removed rather than kept alongside it.

### P1 — Major workflow / integrity risks

**A8. `payroll` had no `UNIQUE(employee_id, month)` constraint** (unlike `attendance`/`payment_status`, which both already have the equivalent). Fixed via `20260803000001_payroll_unique_constraint.sql`. Additionally, **`processPayroll()`/`copyFromPreviousMonth()`'s underlying delete-then-insert was not atomic** — if the insert half failed after the delete half succeeded, that month's payroll was left fully deleted with nothing re-inserted. Addressed with a new, fully-designed atomic RPC: `supabase/migrations/20260803000002_payroll_atomic_process_rpc.sql`'s `process_payroll_batch()` function. It:
- Resolves the caller's tenant/role itself (required — `SECURITY DEFINER` bypasses RLS, so it cannot rely on the table's own policies).
- Takes an advisory transaction lock keyed by tenant+month, serializing concurrent processing attempts.
- Validates every targeted employee belongs to the caller's tenant, and **refuses outright if any targeted employee already has an approved payroll row for that month** — reprocessing can never silently revert an approval to pending.
- Only after validation: deletes, then inserts via a single `INSERT...SELECT` (atomic by construction — no partial-insert state is possible), then writes the audit log entry in the *same* transaction as the data change it describes.
- Any exception at any step rolls back everything, including the delete.

Deliberately does **not** recompute payroll figures itself — that logic stays in TypeScript, unchanged, per the standing rule against altering payroll/tax/pension math without a confirmed source. The migration file itself contains a full staging test procedure (8 scenarios) and rollback SQL. **NOT executed against any database.**

**Update, this pass: now wired to `Payroll.tsx`.** `src/utils/payrollProcessing.ts`'s `processPayrollBatch()` wraps the RPC call and is called from both `processPayroll()` and `copyFromPreviousMonth()`, replacing their previous separate client-side DELETE-then-INSERT entirely. **This is a real deployment-order dependency, unlike the guard-ID/employee-number generation below**: `process_payroll_batch()` has no client-side fallback, so if this code reaches production before the migration is applied there, payroll processing breaks outright (`function process_payroll_batch does not exist`). See "Production deployment and rollback order" below — this specific commit must not ship ahead of its migration. 7 new unit tests (`payrollProcessing.test.ts`) plus a full staging integration suite (`e2e/authenticated/rpc-workflow-matrix.spec.ts`, covering the success path, idempotent reprocessing, approved-month protection, partial-failure rollback, and unauthorized-role rejection — see `TEST_PLAN.md`).

**A20 (new). Guard IDs and employee numbers were generated client-side with no real concurrency safety.** Guard IDs (`` `G-${Math.floor(Math.random() * 1000)}` `` and inconsistent variants) had a ~9,000-value random range with **zero** uniqueness check anywhere — collision probability crosses 50% at ~112 guards (birthday paradox). Employee numbers were computed by querying the browser for the highest existing number matching a region prefix, then incrementing client-side — a read-then-write race under concurrent creation in the same region. **Fixed via two new migrations, both written and NOT applied to any database:**

**Every transition possible through direct Supabase API calls** (confirmed by reading `applicants`'s actual RLS policies in `20260803000000_role_level_rls_hardening.sql`, not assumed): the `UPDATE` policy restricts *who* can write (`role_level <= 2`, i.e. Admin/Manager, or super admin) and *which tenant's* rows, but places **zero restriction on which values** can be written to `interview_status`/`decision` beyond the table's own value-level `CHECK` constraints. This means direct API access allows **strictly more** invalid states than even the loosely-gated UI does:
- Every transition the UI exposes (see the table above) is also directly reachable via the API — unsurprising, since the UI has no server-side backing for its own `disabled={...}` checks; those are purely client-side JavaScript, trivially bypassed by any direct `PATCH`/`supabase.from('applicants').update(...)` call.
- **Additionally, a direct API call can set `interview_status` and `decision` independently, to combinations the UI's own buttons never produce** — e.g. `interview_status: 'Pending', decision: 'Hire'`, or `interview_status: 'Accepted', decision: 'Reject'`. The UI always writes both fields together (see the table above — each button sets a fixed pair), but nothing in the schema enforces that the two fields stay consistent with each other. This is a real gap the UI-only view of this finding would have missed: verified directly, confirmed by this session's own `rpc-workflow-matrix.spec.ts` integration test.

**Recommended state machine (documented here for business approval — NOT implemented anywhere in this pass, per instruction):**

```
Pending → Shortlisted or Rejected
Shortlisted → Interviewed or Rejected
Interviewed → Accepted or Rejected
Accepted → Hired
Hired → terminal state
Rejected → terminal state
```

This is a conservative, linear pipeline — every stage can still end in `Rejected`, but forward progress must go through each intermediate stage in order, and both `Hired` and `Rejected` are terminal (no transitions out). It does not yet reconcile the app's current two-column design (`interview_status` + a separate `decision` field) with the single-status model above — that reconciliation (e.g. folding `decision` into the same state machine as an `Accepted → Hired` step, as sketched here, versus keeping them as two independently-governed fields) is itself part of what needs business confirmation before implementing anything.

**If and only if this (or an amended version of it) is approved**, enforcement should exist at both layers, with the database as the final authority regardless of what the UI allows or hides:
- **Interface**: disable/hide buttons that don't represent a valid transition from the applicant's current status (extending the existing partial `disabled={...}` pattern to cover all four buttons and both hire/reject cases, not just the two that already check `interview_status`).
- **Database**: a trigger (`BEFORE UPDATE ON applicants`) or a dedicated `SECURITY DEFINER` RPC (mirroring the payroll/guard-ID/employee-number pattern elsewhere in this audit) that rejects a disallowed transition outright — so a direct API call bypassing the UI (or a bug in the UI's own disabled-state logic) can never produce an invalid sequence. The UI-only check above is a UX convenience, not a substitute for this, precisely because of the direct-API gap demonstrated above.

**Rollback and correction procedures for an accidental status change** (needed regardless of whether a state machine is ever enforced, since mistakes — a Manager clicking the wrong button, or a direct API call with a typo — can happen either way, and there is currently no dedicated "undo" feature anywhere in `Recruitment.tsx`):
1. **Identify the affected row(s)**: `SELECT id, name, interview_status, decision, created_at FROM applicants WHERE id = '<applicant id>';` — get the current (wrong) state first, before changing anything.
2. **Check for a prior value in `audit_logs`**: `SELECT old_data, new_data, created_at FROM audit_logs WHERE entity_type = 'applicant' AND entity_id = '<applicant id>' ORDER BY created_at DESC LIMIT 5;` — `Recruitment.tsx`'s `update()` function calls `logAudit()` with the pre-change `interview_status`/`decision` as `old_data` (confirmed by reading the function), so the correct prior value is usually recoverable from here rather than guessed at.
3. **Correct the row directly** (no RPC exists for this, since none of this is enforced yet): `UPDATE applicants SET interview_status = '<correct value>', decision = '<correct value>' WHERE id = '<applicant id>';`, run as an Admin/Manager (satisfies the existing RLS policy) — ideally via the Supabase SQL editor with a human reviewing the exact statement, not a bulk script, since this is a one-off correction not a repeatable operation.
4. **Log the correction itself**: this manual fix does not go through `Recruitment.tsx`'s own `update()` function, so it will **not** automatically create its own `audit_logs` entry — insert one manually (`INSERT INTO audit_logs (tenant_id, user_id, user_email, action, entity_type, entity_id, old_data, new_data) VALUES (...)`) documenting that this was a manual correction, by whom, and why, so the audit trail doesn't have an unexplained gap where the fix happened.
5. **If the mistake already triggered a downstream action** (e.g. an `Accepted`+`Hire` applicant was mistakenly converted into an actual `employees` row via whatever manual hiring process the team uses today — recall `handleHireEmployee()` in `clickHandlers.ts`, the one place this might once have been automated, was dead code with a real bug and was deleted this pass, so no automated applicant→employee conversion currently exists at all): that is a separate, employee-record-level correction (see `Employees.tsx`'s own edit/soft-delete flow), not something this recruitment-status rollback alone resolves.

Not implemented in this pass. If a specific transition policy is wanted, that's a product decision to make first — then it can be implemented and tested for real, rather than tested into existence here.

**A22 (new). `payroll` has no historical snapshot of an employee's region/company/site/name at the time that payroll ran — only a live FK to the current `employees` row.** Found while implementing and then security-reviewing the Payroll historical-navigation/export feature (branch `audit/full-system-hardening`). `payroll`'s own columns (`20260727000000_reconstructed_base_schema.sql:288-308`) are `id, tenant_id, employee_id, month`, monetary fields, and approval fields — **no `region_id`, no company/site, no employee name/number**. Every organizational/display field shown next to a historical payroll row (region, company, workstation, name) is resolved by joining `employee_id` to the employee's row **as it exists today**, never a value frozen at processing time.

This creates a real, confirmed split between two things that sound similar but are not:
- **A. Historical monetary preservation** — genuinely correct. `basic_salary`/`gross_pay`/`paye`/`pension`/`uniform_deduction`/`net_pay`/`approval_status` are frozen at processing time and never recalculated by viewing history (verified: the historical branch added by this feature is read-only, no UPDATE/INSERT/DELETE anywhere on that path).
- **B. Historical organizational context** — **not** preserved. If an employee moves from Region A to Region B after May's payroll runs, May's record will show "Region B" (today's value) when viewed later, not "Region A" (the true value at the time).

**This is not merely a display quirk — it is independently enforced by RLS, not just application code.** The active `payroll` SELECT policy (`20260817000002_functional_roles_indirect_region_tables.sql:30-42`) authorizes a row via `EXISTS (SELECT 1 FROM employees e WHERE e.id = payroll.employee_id AND region_allowed(e.region_id))` — `e.region_id` is a live join to the employee's *current* region, not a snapshot. So a non-business-admin, region-scoped caller (e.g. an Accountant or a legacy regional Admin without business-admin status) genuinely **cannot** see a moved employee's pre-move historical payroll at the database level, regardless of any client-side code. The feature's own client-side region filter (`src/pages/Payroll.tsx`, historical branch) intentionally mirrors this same "current region" rule rather than trying to work around it, per explicit instruction not to fabricate historical organizational context from current employee data and label it historical, and not to weaken any authorization check to make history "reappear."

**Deliberately not fixed in this pass** — the correct fix is a schema change (e.g. a `region_id_at_processing`/company/site snapshot captured by `process_payroll_batch()` at the moment payroll is processed, with RLS and every historical read updated to use it instead of the live join), which needs its own design and migration review, not a byproduct of a navigation/export feature. Flagged here for a future pass; no snapshot columns added, no backfill attempted, no existing check removed or weakened.

**A23 (RESOLVED this pass — Option A). `Payroll.tsx`'s live-preview deduction calculation used to read the `attendance` table directly, which a functional-role Accountant is not authorized to read under the active RLS policy.** `fetchData()`'s `Promise.all` (`src/pages/Payroll.tsx`) used to unconditionally fetch `attendance` rows (for absent/late-day deduction figures used only in the current/future month's *unprocessed* live preview — a processed/historical month's stored `payroll` row is used as-is and never needed this data). The active `attendance` SELECT policy (`20260817000002:107-119`) requires `current_user_role_level() IS NOT NULL OR has_permission('attendance.view')`. An Accountant has `role_level = NULL` (functional-role accounts, by design) and no `attendance.view` grant in the seeded permission matrix (`20260817000000:315-333`). Postgres RLS silently returns zero rows for a denied SELECT rather than erroring, so the practical effect was: an Accountant processing the *current* month would see attendance-based deductions silently understated (zero) in the live preview, with no error anywhere in the UI, before then being able to persist that understated payroll via `process_payroll_batch()` (which never itself recomputes or validates these figures — see A24 below).

**Fix implemented**: `supabase/migrations/20260901000000_payroll_attendance_aggregate_rpc.sql` adds `get_payroll_attendance_counts(p_employee_ids UUID[], p_month TEXT)`, a narrow `SECURITY DEFINER` RPC returning only `{employee_id, absent_days, late_days}` (never a raw attendance row, never any other `attendance` column), gated by the same rule as the `payroll` table's own SELECT RLS (`current_user_role_level() IS NOT NULL OR has_permission('payroll.view')`) rather than `attendance.view`, and region/tenant-scoped identically (`region_allowed(e.region_id)`, unauthorized/foreign ids simply absent from the result, never an error and never a leaked row). `Payroll.tsx`'s current/future-month branch now calls this RPC instead of reading `attendance` directly — for both Accountant and Admin, one consistent input path rather than a role-specific branch. `attendance`'s own RLS is completely untouched; Accountant is still not granted `attendance.view` and still cannot browse the Attendance module. **Fail-closed**: if the RPC call fails for any reason, `Payroll.tsx` sets `attendanceCountsUnavailable`, shows a blocking banner ("Unable to load attendance totals required for payroll. Please refresh and try again."), and disables Process Payroll/Reprocess/Copy From Previous Month (both in the UI and as a defense-in-depth guard inside `processPayroll()`/`copyFromPreviousMonth()` themselves) — it never falls back to treating missing attendance data as zero.

Option B (recomputing attendance deductions server-side inside `process_payroll_batch()` itself, closing the broader client-trust gap for every caller including Admin) was explicitly deferred — see new Finding A24.

**Correction to historical-branch terminology**: the historical-month branch displays `employee_deductions.absent_days`/`late_days` (and the derived deduction breakdown) alongside the authoritative, frozen `payroll` monetary row. These `employee_deductions` counts are **not** a guaranteed immutable payroll-processing snapshot — the row is written by Attendance.tsx's manual "Save Deductions" action, independently of `process_payroll_batch()` (which never reads or snapshots `employee_deductions` at all), so it can in principle be edited after the month it describes was processed, silently diverging from whatever `process_payroll_batch()` actually used at the time. Only the monetary fields stored directly on the `payroll` row itself (`gross_pay`/`paye`/`pension`/`uniform_deduction`/`net_pay`) are the authoritative, frozen processed-payroll record.

**A24 (new). `process_payroll_batch()` trusts client-computed payroll monetary values and does not independently recompute or validate their business-formula correctness — a pre-existing gap affecting every caller, not just Accountant.** Read in full (`supabase/migrations/20260817000003_functional_roles_rpc_authorization.sql`): the function's payload validation (STEP 1.5) checks only that `basic_salary`/`allowances`/`overtime`/`bonus`/`gross_pay`/`paye`/`pension`/`uniform_deduction` are well-formed, non-negative numeric strings (`net_pay` may be negative), and that `employee_id` is a well-formed UUID with no duplicates in the batch. It never reads `attendance` or `employee_deductions`, and never recomputes `gross_pay`/`paye`/`pension`/`net_pay` from any server-side source of truth to confirm the submitted figures are actually correct — whatever the client sends (format-valid) is persisted as-is.

This means a stale client cache, a client-side calculation bug, a race between an attendance edit and submission, or (in principle) deliberate tampering with the request payload can already result in an incorrect month's payroll being saved, for **any** caller authorized to call this function — a regular Admin (`role_level = 1`) exactly as much as an Accountant (`has_permission('payroll.process')`). The Accountant/current-month scenario fixed by A23 above did not create this gap; it simply made the gap trivially and non-maliciously reachable (silently zeroed deductions on every current-month run, via ordinary RLS denial, no tampering required) where for other callers today it requires either a bug or deliberate action to trigger.

**Deliberately not fixed in this pass** (approved scope was Option A / A23 only). The more rigorous fix — Option B, having `process_payroll_batch()` independently recompute attendance-based deductions (and validate the resulting gross/net) server-side rather than trusting the client's submitted figures — would close this for every caller, but requires its own explicit design: it changes the contract of the one RPC every existing successful payroll run already depends on (Admin included), and needs an explicit decision on how to handle any legitimate manual override/adjustment case before rejecting a submission that doesn't match the server's own recomputation. Flagged here as a real, currently-open payroll data-integrity gap that should be resolved with its own reviewed migration before this is considered fully closed, not folded silently into a smaller feature change.

## Production deployment and rollback order

None of this branch's migrations or code changes should reach production in one step, and **the frontend must not be deployed before its required RPC migrations exist in production** — `Payroll.tsx` now calls `process_payroll_batch()` directly with no fallback (unlike the guard-ID/employee-number generators, which degrade gracefully). The 10-step sequence below is the safe order; steps 1–4 must all complete before step 6 (frontend deploy) for anything touching the payroll RPC specifically.

1. **Production backup and recovery verification.** Confirm a recent, restorable backup of the production database exists and that the restore procedure has actually been tested (not just assumed to work) — this is a prerequisite this audit cannot perform or verify itself (no production database access), but it must be true before step 3. If Supabase's own point-in-time-recovery/backup plan for this project has never been test-restored, do that first, independent of this migration set.
2. **Preflight data checks.** Run every migration's own `PREFLIGHT SQL` (now included as comments in all 5 migration files) against production, read-only, before applying anything: duplicate `(employee_id, month)` in `payroll`, duplicate `(tenant_id, "guardId")` in `employees`, duplicate `(tenant_id, employee_number)` in `employees`. Any row returned means a real pre-existing duplicate must be manually resolved first (see each migration's own guidance) — do not proceed to step 3 with an unresolved preflight failure.
3. **Apply database migrations**, to staging first, then production, in this order (each migration's own header explains why this order, and `DATA_INTEGRITY_REVIEW.md`'s migration safety table has the lock/blocking-risk detail for each):
   1. `20260803000000_role_level_rls_hardening.sql`
   2. `20260803000001_payroll_unique_constraint.sql`
   3. `20260804000000_guard_id_generation.sql`
   4. `20260804000001_employee_number_generation.sql`
   5. `20260803000002_payroll_atomic_process_rpc.sql`
4. **Verify RPC existence and permissions** immediately after applying, using the `VERIFICATION SQL` now included in each migration file — confirm each function exists with `SECURITY DEFINER` actually set (`pg_proc.prosecdef = true`), confirm `authenticated` has `EXECUTE` and `anon`/`PUBLIC` do not (`has_function_privilege(...)`), confirm expected policies/constraints exist. Do not proceed to step 5 on an unverified migration.
5. **Run smoke tests using safe test records** — the staging-gated Playwright suites (`e2e/authenticated/rls-policy-matrix.spec.ts`, `e2e/authenticated/rpc-workflow-matrix.spec.ts`) against staging with real 4-role credentials, plus each migration's own manual staging test procedure (concurrent calls, legacy-ID handling, cross-tenant separation — see `DATA_INTEGRITY_REVIEW.md`). All test data these suites create is disposable and self-cleaning (see "Verify test-environment isolation" below) — never run against production, only staging.
6. **Deploy frontend** — only after steps 1–5 are complete and verified in production (not just staging). This is the step that must not happen early: deploying `Payroll.tsx`'s RPC call before step 3.5/4 completes in production breaks payroll processing outright (`function process_payroll_batch does not exist`). The guard-ID/employee-number frontend code has no such hard constraint (safe fallback), but deploying it after its migrations anyway is still the more conservative, recommended order.
7. **Verify employee creation, guard creation, and payroll** work end-to-end in production immediately after the frontend deploy — create one real (or disposable, clearly-labeled) employee, confirm a server-generated `SFG-<letter>-NNN` number (not a client-side-random fallback) appears; create one guard, confirm a server-generated `G-NNNN` appears; process one real month's payroll for a small subset of employees, confirm success and that `deletedCount`/`insertedCount` in the response match expectations.
8. **Monitor logs** — Supabase's own function/database logs for the first production calls to each new RPC (watch for unexpected `RAISE EXCEPTION` messages, which would indicate either a real authorization/validation rejection working as intended, or a shape mismatch between what the frontend sends and what the function expects), and application-level error tracking for the guard-ID/employee-number fallback path firing more than expected (would indicate the RPC is failing silently and every call is falling back, not obviously broken but running in a lesser-safety mode).
9. **Roll back the frontend if required** — revert the frontend deploy (step 6) first if anything in step 7/8 looks wrong, before touching the database. The frontend rollback alone restores the guard-ID/employee-number client-side fallback behavior immediately; for payroll specifically, reverting the frontend removes the only caller of `process_payroll_batch()`, which is safe (see step 10) even before the function itself is ever dropped.
10. **Roll back the database only when safe** — only after the frontend no longer calls the affected RPC (step 9), using each migration's own `ROLLBACK SQL`. Apply rollbacks in reverse order of step 3. None of the 5 migrations' rollbacks delete or lose data (see `DATA_INTEGRITY_REVIEW.md`'s migration safety table) — the one exception requiring extra care is `20260803000000_role_level_rls_hardening.sql`'s rollback, which needs each policy's exact prior text restored from its original source migration, not a trivial one-line revert.
